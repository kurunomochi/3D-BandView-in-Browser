01 · 先看清这个博客是怎样运行的

你已经有了一个很适合学习异步工程的项目：访问量不必很大，但它确实会接收网络连接、解析 HTTP、检查登录、共享内存、上传图片、保存文件，并在 Linux 上长期运行。学习目标是能解释这些环节如何协作，而不仅是能写出一个 async fn。

本教程以仓库 5d1e093 的后端结构为基线，编写日期为 2026-10-20。前一次代码整理已拆分模块，但仅凭静态页面上线不能断言服务器二进制也更新了；这里讲的是你本地仓库中的实现。以下将明确区分“当前已有”和“后续练习”，不会把建议当成项目已经具备的功能。

浏览器→HTTPS 反向代理→TCP / HTTP→Axum 路由→处理函数→内存 / JSON 文件

首页首先请求 HTML、CSS、JavaScript 和视频，随后 public/script.js 通过 fetch("/api/posts") 取得文章数组。网页不是直接读取磁盘上的 posts.json：启动时后端把数据加载到内存，GET 接口再从共享状态读取。

文件 职责 重点问题
src/main.rs 启动、状态组装、路由、停止信号 哪个 Future 长期运行？
src/config.rs 读取环境变量 为什么在开始接请求前校验？

tests/integration.mjs 启动独立进程测试 重启后还在，才算真的持久化了吗？

一个请求有两条路径

读文章：收到 GET → 路由匹配 → 提取 State → 申请读锁 → 克隆结果 → 释放锁 → 序列化 JSON → 发回响应。保存文章：收到 POST → 检查令牌 → 解析 JSON → 校验 → 申请写锁 → 生成新副本 → 保存文件 → 替换内存 → 返回 201。

先顺着这两条路径读代码。以后再引入数据库、消息队列或缓存，你仍然需要回答同样的问题：谁拥有数据，谁可以同时修改，什么时候对外承诺成功？

02 · TCP、HTTP、HTTPS 和端口，分别负责什么

把网络层次拆开

IP 让数据能够被发送到网络中的目标地址；端口帮助操作系统把流量交给某个套接字；TCP 提供可靠、有序的字节流；HTTP 在这些字节上定义请求方法、路径、头部、正文和响应状态。TLS 增加加密和身份校验，常见的 HTTPS/HTTP 1.1、HTTP/2 使用它。HTTP/3 使用 QUIC/UDP，所以“所有 HTTP 都走 TCP”并不准确。本项目 Rust 端明确监听的是 TCP。

已有部署中，浏览器访问域名的 HTTPS 服务，Apache 再把请求转给服务器内的 Rust 端口。公网 TLS 在代理处处理，Rust 看到的是回环地址上的 HTTP。两段连接是不同的连接；代理可能复用后端连接，不能假定“一个浏览器对应一个后端 TCP socket”。

地址 含义
127.0.0.1:3000 只接受本机回环接口上的连接，适合反向代理后面的服务
0.0.0.0:3000 绑定所有 IPv4 本地接口；实际是否公网可达还取决于防火墙/NAT
127.0.0.1:0 请操作系统分配一个可用端口，适合自动测试
域名:443 通常是 HTTPS 入口；域名经 DNS 解析后再连接 IP

TCP 建立连接与传输

典型连接建立过程是 SYN → SYN-ACK → ACK。这个握手建立 TCP 状态，不代表网站登录成功。TCP 通过序号、确认、重传等机制处理丢失和顺序；拥塞控制关注网络承受能力，流量控制关注接收端承受能力。它们都不能替你的业务判断“文章有没有写入 JSON”。

服务端的 TcpListener 是监听入口。每次 accept() 得到一个新的 TcpStream，代表一条已建立连接；accept 不等于读到了完整 HTTP 请求。监听端口可以服务许多连接，操作系统用两端地址和端口等信息区分它们。

连接复用、关闭和成功确认

HTTP/1.1 通常支持持久连接，一条 TCP 连接可以处理多个请求。HTTP/2 还支持在一个连接里复用多个流；具体是否启用由客户端、代理和服务配置决定。不要从 TCP 连接数直接推算同时执行的业务请求数。

对非空缓冲区读取时，read 返回 0 通常表示对端发送方向已经结束且已无剩余数据。TCP 可以半关闭：对端不再发送，但仍可以接收。write_all 成功只表示这些字节已被本地写出接口接受，不表示对方应用已处理、更不表示对方磁盘已经保存。

03 · async / await 的真正含义

async fn 调用产生一个 Future，可以理解为“保存了执行进度的计算对象”。它不会自动为你创建线程。普通 async 函数体在 Future 被轮询时才推进；把 Future 放在变量里、不 await 也不提交给运行时，函数体就不会自己完成。

rust 
async fn load_title() -> String {
    println!("函数体开始");
    "我的博客".to_owned()
}

// 在 async 上下文里：
let future = load_title(); // 还没有打印
println!("先执行这里");
let title = future.await; // 驱动 Future，得到 String

.await 会发生什么

如果被等待的操作已经完成，执行可以继续，不一定切换任务。如果尚未就绪，当前任务返回等待状态，运行时有机会处理其他任务；资源就绪后通过唤醒机制让它再次被调度。因此，“异步等待不占住工作线程”有前提：所调用的实现确实能及时让出执行权。

Future 接口中的 Poll::Ready(value) 表示完成，Poll::Pending 表示暂不能完成。Waker 是通知调度器“这个任务可能可以继续了”的机制，而不是直接执行后续业务。Tokio 负责把任务调度与网络、定时器等事件衔接起来，应用代码通常不需要自己实现 poll。

把 create_post 想象成状态机：尚未取得锁 → 等待写锁 → 已有新文章副本 → 等待文件保存 → 更新内存 → 返回。跨等待点仍要使用的局部变量需要保存在 Future 中，所以大缓冲区、借用和锁守卫都会影响任务的内存及生命周期。

不要把 .await 当成“开一个后台线程”，也不要以为每次 await 都必然暂停。你可以先会使用 Future；Pin 的详细实现可以放到第二轮学习，但需要知道它用于约束某些值在被固定后不能随意移动，并不是“锁定到某个线程”。

04 · Tokio 运行时与项目启动

Rust 语言提供 Future/async/await 的基础机制；Tokio 提供运行它们需要的调度器、I/O 支持、定时器及同步原语。#[tokio::main] 为程序建立运行时，再驱动 async main。项目启用了 rt-multi-thread，使用默认的多线程运行时；不需要手动为每个 HTTP 请求创建系统线程。

启动和接请求是两个阶段。当前 main 先读配置、检查静态目录、加载文章和作品、构建状态，最后绑定端口开始服务。加载阶段的几个 await 按代码顺序执行，这里选择顺序初始化便于失败定位，不是因为异步代码只能串行。

项目源码 · src/main.rs:83

rust 
let listener = TcpListener::bind(config.bind).await?;
    println!("blog server listening on http://{}", listener.local_addr()?);
    axum::serve(listener, app)
        .with_graceful_shutdown(shutdown_signal())
        .await?;
    Ok(())
}

bind(...).await? 得到监听器。axum::serve(listener, app) 返回服务相关对象，末尾的 await 驱动服务长期运行；它不会在处理完一个请求后就退出。框架内部负责接受连接与处理 HTTP，你只需要提供业务路由。

为什么用了 .await?

很多异步 I/O 的结果是 Future<Output = Result<T, E>>。await 先得到 Result，问号再把错误向调用者传播：成功取出 T，失败提前返回。问号不会重试，不会忽略错误，也不会自动把网络错误变成 HTTP 500；是否能转换到目标错误类型，取决于函数签名及转换实现。

Cargo 的 feature 是编译期能力选择

本项目的 Tokio 配置启用了 macros、rt-multi-thread、fs、net、sync、signal、io-util。配套练习在 dev-dependencies 中显式启用了 time，用于 sleep 和 timeout。feature 不是运行时开关；新增功能后缺少对应 feature，常会看到模块无法导入。

05 · 顺序、并发、并行与 spawn

并发指多个任务在一个时间段内交错推进；并行指在同一时刻由多个执行单元同时工作。一个线程也能并发等待许多连接，多线程也不保证你的业务一定变快。先判断工作时间主要花在“计算”还是“等待”。

写法 执行方式 注意点
a().await; b().await; 先等 A 完成，再开始 B 适合有先后依赖的步骤
tokio::join!(a(), b()) 在当前任务中并发轮询两个 Future 不创建两个独立线程；一支阻塞会拖住另一支
tokio::spawn(a()) 创建由运行时调度的独立任务 Future 通常要 Send + 'static
tokio::select! 并发等待，选择某个就绪分支执行 未选中的分支 Future 会被丢弃，需考虑取消

特别容易混淆的是 JoinHandle：spawn 已经把任务交给运行时，稍后 await handle 是等待它的结果，不是那时才让任务开始。丢弃 JoinHandle 通常只是放弃获取结果，任务会继续；显式 abort 才请求取消。运行时退出也不会让你的所有后台工作神奇地保存完成。

终端 
cargo run --example async_basics

你会先看到“Created a future”，再看到 lazy 任务的 started。顺序两个 300ms 等待通常约 600ms，join 通常约 300ms；实际耗时受调度和系统负载影响，这只是语义演示，不是精确基准。观察 spawned 的输出次序可能变化，不能依赖某个固定调度顺序。

rust 
//! Run: cargo run --example async_basics
use std::time::Instant;
use tokio::time::{Duration, sleep};

async fn job(name: &'static str) -> &'static str {
    println!("{name}: started");
    sleep(Duration::from_millis(300)).await;
    println!("{name}: finished");
    name
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let not_started = job("lazy");
    println!("Created a future; its body has not run yet.");
    not_started.await;

    let start = Instant::now();
    job("sequential A").await;
    job("sequential B").await;
    println!("sequential: {:?}", start.elapsed());

    let start = Instant::now();
    let (a, b) = tokio::join!(job("joined A"), job("joined B"));
    println!("join: {a}, {b}, {:?}", start.elapsed());

    let handle = tokio::spawn(async move { job("spawned").await });
    println!("The spawned task can progress before we await its handle.");
    println!("task result: {}", handle.await?);
    Ok(())
}

06 · 先写一个 TCP 字节回显服务器

为了看见 Axum 下面的一层，我们暂时绕开 HTTP：服务端收到什么字节，就回传什么字节。练习在回环地址 127.0.0.1:4000 运行，不读取博客配置或文章数据。

终端 
# 终端一：保持运行
cargo run --example tcp_echo

# 终端二：发送两条带长度头的测试消息
cargo run --example tcp_frames -- client 127.0.0.1:4000

客户端虽然使用了长度头，但字节回显服务不理解它，只是原样返回全部字节；客户端再按自己的规则解码，因此也能完成往返。这正说明：TCP 只负责字节传输，消息语义由端点协议决定。别用浏览器访问这个端口来验证网页，它不是 HTTP 服务。

rust 
let n = stream.read(&mut buffer).await?;
if n == 0 {
    return Ok(());
}
stream.write_all(&buffer[..n]).await?;

buffer 是可重复使用的 4096 字节数组，n 是这次实际读到的字节数，不是总消息长度。只写 &buffer[..n]，否则可能把缓冲区里上一次的残留数据也发回去。write_all 会尝试把整个切片交给写入接口；普通 write 可能只写一部分。

为什么 accept 后要 spawn

如果你在 accept 循环里直接 echo(socket).await，就要等这个连接处理结束，才继续接受下一条连接。示例把每条连接放入 JoinSet 管理的任务，监听循环便能继续。JoinSet 还让我们回收已完成任务的结果，而不是积攒无人检查的句柄。

我们用 Semaphore 把同时处理的连接限制为 32；超过时关闭新连接。读写各有 30 秒超时。读超时每次读到字节后重置，因此它是“空闲超时”，并不是整个连接的最长寿命。示例停止时取消现有连接，适合无持久化的回显实验，不是博客写入停机策略。

rust 
//! Byte-stream echo server, not an HTTP server.
//! Run: cargo run --example tcp_echo
//! Connect with: cargo run --example tcp_frames -- client 127.0.0.1:4000
use std::{io, sync::Arc, time::Duration};
use tokio::{
    io::{AsyncReadExt, AsyncWriteExt},
    net::{TcpListener, TcpStream},
    sync::Semaphore,
    task::JoinSet,
    time::timeout,
};

async fn echo(mut stream: TcpStream) -> io::Result<()> {
    let mut buffer = [0_u8; 4096];
    loop {
        // Idle read deadline: it resets after each successful read.
        let n = timeout(Duration::from_secs(30), stream.read(&mut buffer))
            .await
            .map_err(|_| io::Error::new(io::ErrorKind::TimedOut, "idle connection"))??;
        if n == 0 {
            return Ok(());
        }
        timeout(Duration::from_secs(30), stream.write_all(&buffer[..n]))
            .await
            .map_err(|_| io::Error::new(io::ErrorKind::TimedOut, "slow reader"))??;
    }
}

#[tokio::main]
async fn main() -> io::Result<()> {
    let listener = TcpListener::bind("127.0.0.1:4000").await?;
    let permits = Arc::new(Semaphore::new(32));
    let mut tasks = JoinSet::new();
    println!("Byte echo listening on 127.0.0.1:4000; Ctrl+C stops the demo.");
    loop {
        tokio::select! {
            signal = tokio::signal::ctrl_c() => {
                signal?;
                break;
            }
            result = tasks.join_next(), if !tasks.is_empty() => {
                if let Some(Err(error)) = result {
                    eprintln!("Task failed: {error}");
                }
            }
            accepted = listener.accept() => {
                let (socket, peer) = accepted?;
                let Ok(permit) = permits.clone().try_acquire_owned() else {
                    // Demo overload policy: close the new connection immediately.
                    drop(socket);
                    continue;
                };
                tasks.spawn(async move {
                    let _permit = permit;
                    if let Err(error) = echo(socket).await {
                        eprintln!("{peer}: {error}");
                    }
                });
            }
        }
    }
    // This demo has no persistent writes; intentionally abort in-flight echoes.
    // A data-writing service needs a drain/commit policy instead.
    tasks.abort_all();
    while tasks.join_next().await.is_some() {}
    Ok(())
}

07 · TCP 没有消息边界：把“粘包”还原成字节流

你连续发送 HELLO 与 WORLD，接收方可能读到 HEL，下一次读到 LOWOR，最后读到 LD；也可能一次读到全部。应用的 write/read 调用边界，与 TCP 报文段、网卡分段及操作系统缓冲处理不是同一个概念。

所谓“粘包”和“半包”，通常是程序错误地把一次 read 当成一条完整消息。解决问题靠应用层分帧：固定长度、分隔符、长度前缀，或使用已经定义好边界规则的协议。HTTP 已有成熟解析器，不要在博客里自己随意拆字符串替代它。

本练习的协议

格式为 4 字节大端无符号长度 + payload 原始字节。例如 RUST 的帧是 00 00 00 04 52 55 53 54。长度按字节计算；中文 UTF-8 字符常占多个字节，不能拿字符个数当网络长度。

分帧演示：一次读取不等于一条消息

预设两帧 RUST、HI，模拟它们以三次不规则读取到达。这里模拟应用 read 的结果，不模拟真实 TCP 报文。

尚未接收字节

待解析缓冲区：空

已完成消息：无

read_exact 会持续读取直到指定缓冲区填满，或者返回错误。先拿到长度，再检查最大值，最后分配正文缓冲区。这一顺序很重要：攻击者发来极大长度时，不能先申请内存再校验。

示例最大正文 64 KiB，允许空消息，连接可以连续传多帧。新帧开始前干净 EOF 返回 None；头部或正文读一半就结束则返回 UnexpectedEof。每个完整帧有 30 秒期限；超时后直接关闭连接，因为被取消的 read_exact 可能已消费部分字节，不能假装下一字节仍是新帧开头。

//! A tiny framed protocol: [4-byte big-endian length][payload].
//! Server: cargo run --example tcp_frames
//! Client: cargo run --example tcp_frames -- client
//! Tests:  cargo test --example tcp_frames
use std::{io, sync::Arc, time::Duration};
use tokio::{
    io::{AsyncRead, AsyncReadExt, AsyncWrite, AsyncWriteExt},
    net::{TcpListener, TcpStream},
    sync::Semaphore,
    task::JoinSet,
    time::timeout,
};

const MAX_FRAME: usize = 64 * 1024;

async fn read_frame<R: AsyncRead + Unpin>(reader: &mut R) -> io::Result<Option<Vec<u8>>> {
    let mut header = [0; 4];
    // Clean EOF before a new header is different from a truncated frame.
    if reader.read(&mut header[..1]).await? == 0 {
        return Ok(None);
    }
    reader.read_exact(&mut header[1..]).await?;
    let length = u32::from_be_bytes(header) as usize;
    if length > MAX_FRAME {
        return Err(io::Error::new(
            io::ErrorKind::InvalidData,
            "frame exceeds 64 KiB",
        ));
    }
    let mut payload = vec![0; length];
    reader.read_exact(&mut payload).await?;
    Ok(Some(payload))
}

async fn write_frame<W: AsyncWrite + Unpin>(writer: &mut W, payload: &[u8]) -> io::Result<()> {
    if payload.len() > MAX_FRAME {
        return Err(io::Error::new(
            io::ErrorKind::InvalidInput,
            "frame exceeds 64 KiB",
        ));
    }
    writer
        .write_all(&(payload.len() as u32).to_be_bytes())
        .await?;
    writer.write_all(payload).await
}

async fn connection(mut socket: TcpStream) -> io::Result<()> {
    loop {
        // A deadline for the whole frame, including its body.
        // On timeout we DROP the connection: read_exact may have consumed bytes.
        let frame = timeout(Duration::from_secs(30), read_frame(&mut socket))
            .await
            .map_err(|_| io::Error::new(io::ErrorKind::TimedOut, "frame timeout"))??;
        let Some(payload) = frame else {
            return Ok(());
        };
        timeout(Duration::from_secs(30), write_frame(&mut socket, &payload))
            .await
            .map_err(|_| io::Error::new(io::ErrorKind::TimedOut, "write timeout"))??;
    }
}

async fn serve() -> io::Result<()> {
    let listener = TcpListener::bind("127.0.0.1:4001").await?;
    let permits = Arc::new(Semaphore::new(32));
    let mut tasks = JoinSet::new();
    println!("Framed echo on 127.0.0.1:4001; Ctrl+C stops the demo.");
    loop {
        tokio::select! {
            signal = tokio::signal::ctrl_c() => {
                signal?;
                break;
            }
            result = tasks.join_next(), if !tasks.is_empty() => {
                if let Some(Err(error)) = result {
                    eprintln!("Task failed: {error}");
                }
            }
            accepted = listener.accept() => {
                let (socket, peer) = accepted?;
                let Ok(permit) = permits.clone().try_acquire_owned() else {
                    drop(socket);
                    continue;
                };
                tasks.spawn(async move {
                    let _permit = permit;
                    if let Err(error) = connection(socket).await {
                        eprintln!("{peer}: {error}");
                    }
                });
            }
        }
    }
    tasks.abort_all();
    while tasks.join_next().await.is_some() {}
    Ok(())
}

async fn client(address: &str) -> io::Result<()> {
    let mut stream = TcpStream::connect(address).await?;
    for text in ["你好，Rust async", "同一条 TCP 连接上的第二条消息"] {
        write_frame(&mut stream, text.as_bytes()).await?;
        let reply = read_frame(&mut stream)
            .await?
            .ok_or_else(|| io::Error::new(io::ErrorKind::UnexpectedEof, "missing reply"))?;
        assert_eq!(reply, text.as_bytes());
        println!("Echo: {}", String::from_utf8_lossy(&reply));
    }
    stream.shutdown().await?;
    Ok(())
}

#[tokio::main]
async fn main() -> io::Result<()> {
    let args: Vec<_> = std::env::args().collect();
    if args.get(1).is_some_and(|arg| arg == "client") {

    }

09 · Arc、Mutex、RwLock：共享不等于随便修改

HTTP 请求可以重叠执行。如果每个请求都创建自己的 Vec，保存后别人看不到；如果多个请求直接修改同一份 Vec，就必须协调访问。项目把全部应用状态放在一个 Arc 内，再分别给不同集合加锁。

项目源码 · src/main.rs:24

    posts: RwLock<Vec<posts::Post>>,
    works: RwLock<Vec<works::Work>>,

    login_attempts: Mutex<Vec<Instant>>,

    admin_password: String,

Arc 管所有权，锁管访问规则

Arc::clone(&state) 增加引用计数，得到指向同一 AppState 的另一个拥有者，不会复制全部文章。最后一个 Arc 释放时才销毁共享对象。Arc 本身不允许任意可变访问，也不能自动把一个不安全的内部类型变安全。

RwLock 允许多个读守卫并存，写守卫独占；Mutex 每次只允许一个守卫。不该用“读多写少就一定更快”代替测量，调度、持锁时间和数据复制成本都可能成为瓶颈。

项目源码 · src/posts.rs:42

rust 
async fn list_posts(State(state): State<SharedState>) -> Json<Vec<Post>> {
    Json(state.posts.read().await.clone())
}

这里 read().await 等待取得读锁，然后 clone 的是 Vec 和其中的文章数据，与 Arc 的浅克隆不同。返回独立 Vec 后不再需要把锁跨越 JSON 序列化和网络发送；好处是缩短读锁范围，代价是文章多时复制昂贵。

为什么不是所有地方都必须 Tokio Mutex

对于很短的同步临界区、不跨 await、争用很小的代码，标准库 Mutex 也可以合理使用。若等锁时阻塞系统线程，或者持同步守卫跨 await，就容易拖住运行时甚至死锁。异步锁让“等待拿锁”可以让出任务，但已经拿到锁后，其余请求仍要遵守访问限制。

本项目 login_attempts 用 Tokio Mutex，只做保留时间窗口和插入时间戳后就 drop(attempts)，因此不会把这个锁带到后续 sessions 写锁中。drop 是主动缩短临界区；更通用的写法是用一个小作用域让守卫自然释放。

rust 
{
    let mut attempts = state.login_attempts.lock().await;
    // 只处理这个集合
} // guard 离开作用域，自动解锁
// 这里再访问其他状态

10 · 保存文章：为什么持着写锁去 await 文件 I/O

“锁尽量短”是一条优化方向，但不能为了短就破坏正确性。当前实现特意把写锁覆盖整个“读取旧集合 → 生成新集合 → 写磁盘 → 发布到内存”的过程。

项目源码 · src/posts.rs:73

rust 
let mut posts = state.posts.write().await;
    let mut updated = posts.clone();
    updated.push(post.clone());
    storage::save(&state.data_file, &updated).await?;
    *posts = updated;
    Ok((StatusCode::CREATED, Json(post)))
}

第一行保证本进程中同时只有一个文章修改者。updated 是旧集合的副本，修改暂不影响读者能看到的数据。storage::save 成功后才把 updated 放回共享状态；文件保存返回错误时，问号提前返回，旧内存集合不变。

过早放锁为什么会丢更新

时刻 请求 A 请求 B
1 从 [旧文章] 克隆副本并放锁
2 也从 [旧文章] 克隆副本并放锁
3 写入 [旧文章, A]
4 写入 [旧文章, B]，覆盖 A

数据竞争在 Rust 的内存安全意义上可能已经避免，业务上的“丢更新”却仍然发生。当前写锁可以避免这个时序，但代价是文章的读请求和其他写请求会在保存期间等待。作品使用另外一把锁，因此不被同一文章锁直接阻塞。

项目源码 · src/storage.rs:16

rust 
pub async fn save<T: Serialize>(path: &Path, values: &[T]) -> Result<(), AppError> {
    let bytes = serde_json::to_vec_pretty(values).map_err(AppError::storage)?;
    let temporary = path.with_extension("json.tmp");
    let result = async {
        let mut file = fs::File::create(&temporary).await?;
        file.write_all(&bytes).await?;
        file.sync_all().await?;
        drop(file);
        fs::rename(&temporary, path).await
    }
    .await;
    if result.is_err() {
        let _ = fs::remove_file(&temporary).await;
    }
    result.map_err(AppError::storage)
}

临时文件、刷盘、重命名，各有不同作用

serde_json::to_vec_pretty 是同步 CPU 工作，即使放在 async 函数里也不会自动异步化。随后创建同目录临时文件、写完整内容、sync_all，再 rename 到目标路径。关闭文件句柄后再重命名，也减少跨平台文件占用问题。

同文件系统上的替换可避免正常读者看到“半个 JSON”，但它不是完整数据库事务。sync_all 用于要求操作系统同步文件数据及相关元信息；严格断电恢复还涉及目录项持久化及文件系统语义，当前代码没有同步父目录。已有的失败回滚测试主要验证普通 I/O 错误，不等于验证断电或所有取消时序。

当前方案仅支持一个进程管理同一数据目录：临时文件名固定，RwLock 也只在一个进程内生效。不要启动两个副本共用这两个 JSON。外部手动修改文件也不会自动刷新内存，需要明确的重新加载流程。

还要区分“普通 Err”和“Future 被取消”：当前 save 的错误清理并不会在 Future 被直接丢弃时自动执行。Tokio 文件操作底层可能仍在阻塞线程池执行，取消时可能出现磁盘已更新但内存尚未更新，甚至后续写入复用临时文件的风险。若以后给写接口加 timeout 或主动 abort，必须先重设计提交边界；不能仅把 save 包进 timeout 就宣布安全。

11 · Result、错误转换与 HTTP 失败语义

系统里至少有四种失败：输入不合法、认证失败、业务对象不存在、基础设施故障。它们不应全部变成 panic，也不应全部返回 200。当前 AppError 用枚举区分业务错误，IntoResponse 决定如何告诉浏览器。

项目源码 · src/error.rs:8

rust 
#[derive(Debug)]
pub enum AppError {
    BadRequest(String),
    Unauthorized,
    NotFound,
    TooManyRequests,
    Internal,
}

    pub fn storage(error: impl std::fmt::Display) -> Self {
        eprintln!("Storage error: {error}");
        Self::Internal
    }

例如 fs::write(...).await.map_err(AppError::storage)?：先等待 I/O，失败时记录底层错误并转换成 AppError，再用问号把它返回。storage 函数中的 impl Display 允许不同的可展示错误进入同一转换入口，不要求把服务器的完整路径和底层信息都发给用户。

状态码 本项目含义 客户端应该怎样理解
200 / 201 / 204 读取成功 / 创建成功 / 无正文成功 204 不能无条件 response.json()
400 业务输入校验不通过 修正表单内容
401 缺少或失效的登录凭据 重新登录，不要无限重试
404 不存在的对象或 API 路径 检查 id 或链接
413 请求体超出限制 缩小上传文件或内容
429 一分钟登录尝试过多 按 Retry-After 等待
500 存储等内部错误 查看服务端日志，保留用户编辑内容

Axum 对 JSON 格式、Content-Type 等提取失败也有自己的拒绝响应，不一定使用你的 AppError JSON 结构。因此前端 common.js 先检查 HTTP 状态，再尝试解析响应体。网络断开则可能连 HTTP 状态码都没有：fetch 抛出错误，并不等于服务端完全没做事。

为什么请求超时后重试可能重复创建

服务端已经把文章保存了，但响应没到浏览器，浏览器只看到超时。如果重试 POST，当前接口会生成另一个 UUID，可能出现两篇文章。UUID 解决标识唯一，不解决重试幂等。未来可增加幂等键并持久化“请求键 → 创建结果”，让同一个逻辑操作重试时得到同一结果。

调试时区分 panic、JoinError 和业务 Result：如果 spawn 的任务返回 Result，那么 handle.await 先得到任务是否成功结束的结果，内层才是业务是否成功。两层问号处理的是两个不同故障层次。

    // 返回 io::Result<Vec<u8>>
    tokio::fs::read("some-file.txt").await
});
let bytes = handle.await??;

12 · 超时、select! 与取消：停止等待不等于撤销操作

给读接口、外部调用设置期限有助于避免无限等待。但 timeout 的含义是：在未来某次运行时检查到超时后，不再继续等待被包装的 Future。它不是操作系统级的强制抢占，也不等于远端事务已经回滚。

rust 
let result = tokio::time::timeout(
    std::time::Duration::from_secs(3),
    some_async_operation(),
).await;
// Ok(inner)：Future 在期限内完成
// Err(elapsed)：等待到期；需要单独分析已发生的副作用

如果 some_async_operation 长时间执行同步计算、不让出控制权，timeout 不能立即打断这段计算。若异步操作向外部系统发出了请求，即使本地 Future 被丢弃，外部系统仍可能完成工作。应该分别考虑“等待期限”“执行期限”“提交是否完成”和“是否可重试”。

取消安全不是所有 async 函数共有的属性

在 select! 中反复取消再重建某个读取 Future，必须知道它是否已经消费了输入。read_exact 被取消时可能已经读走一部分字节；如果你丢失这份进度，再把后续字节当新消息头解析，协议就错位了。分帧示例选择超时就关闭整条连接，避免在未知中间状态继续读取。

需要继续复用连接时，可以把缓冲区和解析进度保存在连接对象中，让取消“等待”不丢失协议状态。对保存文章，则需要更明确的写入工作单元：提交过程一旦进入关键阶段，由受管理的写任务完成并报告结果，而不是任意丢弃它。

不要为了“让 HTTP 快点返回”，就把保存操作随手 tokio::spawn 后立即返回 201。这样 201 可能发出时文件还没有保存，失败也无处反馈；服务退出时任务还可能丢失。先定义成功语义，再选择任务结构。

13 · 上传、背压与阻塞工作

异步可以降低大量等待任务占用线程的成本，但不会消除内存、磁盘、CPU 和文件描述符的上限。一个连接读入 20 MiB 图片，100 个同类上传仅正文缓冲就可能接近 2 GiB，另有代理缓冲、序列化和其他开销。

当前上传实现做了什么

works.rs 为上传路由设置了 20 MiB 的 DefaultBodyLimit，guard 先检查登录；Bytes 提取器把请求正文聚合到内存，handler 检查 PNG/JPEG/WebP 文件头，生成 UUID 文件名，再写到 uploads。它没有逐块转存，也没有完整解码图片或自动压缩。

所以“单个上传有限制”不等于“总上传内存已受限”。进一步改进可以在正文聚合之前放置并发限制，让超出的请求等待或返回明确错误；若在拿到 Bytes 后才申请许可，内存占用已经发生了。

背压是把承受能力传回上游

Semaphore 控制同时进行的工作数量；有界 mpsc channel 控制排队数量，队列满时 send().await 等待。两者管的不是同一件事。无界队列可能把短时间过载变成持续增长的内存；只限制“在执行的任务”，但无限积攒“等待执行的任务”，同样不完整。

TCP 自己也会施加背压：对端读得慢时，发送缓冲逐渐填满，write_all 可能等待。但这只能缓解该连接的发送，不能限制你业务层提前生成的大量响应和任务。

同步 CPU 与异步 I/O 混用

serde_json 编解码、图片缩放、压缩和哈希计算都可能是同步 CPU 工作。小对象内联处理通常简单合理；大对象持续占用工作线程，就会让无关请求延迟升高。先测量，再考虑把重活交给 spawn_blocking、独立工作线程或专门的 CPU 线程池。

rust 
let output = tokio::task::spawn_blocking(move || {
    expensive_synchronous_operation(input)
}).await?;

spawn_blocking 使用单独的阻塞工作线程，不是把同步函数改造成可在任意点暂停的 Future。已经开始的闭包一般不能靠 abort 停止；CPU 密集任务还应该限制并发，避免制造过多竞争线程。Tokio 的普通文件 API 本身也会利用阻塞工作线程，因此“async 文件读取”不等于磁盘硬件原生按 Future 工作。

进一步阅读：Tokio spawn_blocking 文档。

14 · async move、Send、Sync 和 'static

普通函数局部借用通常能顺着调用栈理解。异步任务可能在当前函数返回后仍继续执行，因此编译器要检查：任务拿着的数据是否还活着？能否被调度到别的工作线程？

rust 
let message = String::from("hello");
let handle = tokio::spawn(async move {
    println!("{message}");
});
handle.await?;

async move 把捕获的值移入 Future，让任务自己拥有 message。它不意味着复制，也不意味着创建线程，更不会把一个引用自动变成拥有的数据。如果传进去的是 &String，那移动进去的仍然只是引用；必要时先克隆 String 或 Arc。

术语 应该怎样理解 不应该怎样理解
Send 值可以安全地跨线程转移所有权 这个类型自动并行执行
Sync 共享引用 &T 可以安全地跨线程使用 所有方法都自动加锁
'static 约束 不包含比任务需求更短的外部借用 这个值必须永远占着内存
async move 把捕获值的所有权移入 Future 把一切都变成深拷贝
Arc<T> 多个拥有者引用同一个 T 内部任何 T 都自动线程安全

Tokio spawn 通常要求 Future 是 Send + 'static。这使运行时能够在工作线程间调度任务；并不表示每次 await 后一定换线程。'static 约束也不妨碍任务完成时释放自己拥有的 String。真正的静态引用 &'static str 与泛型 T: 'static 是两个需要区分的写法。

看到“future cannot be sent between threads safely”怎么办

从错误指出的 await 往前看：有哪些值活过了这个等待点？常见的是 Rc、某些锁守卫、线程绑定对象，或借用了短生命周期局部变量。先缩小作用域，确认值在 await 前已释放；若需要跨任务共享，再考虑 Arc 与合适的同步结构。不要为消除报错而盲目增加 unsafe。

本项目 State<Arc<AppState>> 避免把请求借用到一个即将结束的栈帧里；data_file 是拥有的 PathBuf，输入正文是拥有的 String/Vec，适合让请求 Future 在等待磁盘期间保存自己的状态。

15 · 部署与优雅停止：异步程序也有生命周期

一个长期运行的服务器不仅要能启动，还要知道什么时候停止接受工作、怎样等待已接受的工作、何时必须结束。main 中把 shutdown_signal 交给 with_graceful_shutdown，就是把“接到停止信号”接入服务生命周期。

项目源码 · src/main.rs:108

rust 
async fn shutdown_signal() {
    let ctrl_c = async {
        tokio::signal::ctrl_c()
            .await
            .expect("cannot install Ctrl+C handler");
    };
    #[cfg(unix)]
    let terminate = async {
        tokio::signal::unix::signal(tokio::signal::unix::SignalKind::terminate())
            .expect("cannot install SIGTERM handler")
            .recv()
            .await;
    };
    #[cfg(not(unix))]
    let terminate = std::future::pending::<()>();
    tokio::select! { _ = ctrl_c => {}, _ = terminate => {} }
}

Ctrl+C 通常对应中断信号；Linux 上 systemd 停止服务通常发 SIGTERM。select! 等待其中一个到来。非 Unix 平台用永不完成的 pending Future 占住另一个分支，让代码保留同样结构。

服务收到退出通知后可以停止接受新工作并等待已有连接或请求结束；实际等待时间还受慢连接、长请求、HTTP 行为和外部进程管理器的期限影响。当前程序没有给每个写入设计独立的强制取消策略，示例 systemd 文件则设置了 30 秒停止期限，到期后的强制终止不能靠 Rust 析构器保证完成保存。

本地地址、代理和健康检查

原生运行时让 Rust 监听回环地址，代理对外提供 HTTPS。若改成容器，容器内通常需要监听 0.0.0.0，主机端口映射仍可只绑定 127.0.0.1。把容器内部 0.0.0.0 和主机对公网开放混为一谈，会导致“服务正常启动但代理连不上”等问题。

/api/health 当前只返回进程可响应的状态，不检查磁盘剩余空间或未来写入能否成功。健康检查成功说明它能回答这个请求，不代表所有业务依赖都健康。以后可以区分存活检查和就绪检查，但不要在每次健康检查中做昂贵的磁盘操作。

现象 先检查什么
Connection refused 进程是否运行、IP/端口是否正确、是否监听了预期接口
502 / 503 反向代理到后端的连接与健康状态
页面能开，保存失败 后台会话、API 状态码、数据目录权限和磁盘空间
重启后文章不见 BLOG_DATA_DIR、工作目录、容器挂载是否一致
改了样式仍看不到 HTML 的资源版本号、浏览器及 CDN 缓存

项目启动时的静态文件存在检查使用同步 is_file，这种启动阶段的一次小检查与请求处理期间反复读取大文件不同。异步工程判断是否需要改造时，要同时看耗时、调用频率和所在阶段。

17 · 这个工程接下来应该怎样演进

对个人站点，JSON + 单实例 + 集合锁足够易懂。值得学习的是认识它的成本：每次写入克隆整个集合并重写整个文件；列表读取复制全部正文；文件 I/O 期间文章写锁占用；多进程没有协调；没有持久会话和幂等提交记录。

用“单写任务”理解 actor 模型

HTTP 请求→有界 mpsc→写任务拥有状态→提交到存储→oneshot 返回结果

HTTP 层发送命令后，必须等待提交结果才能返回“保存成功”。写任务拥有状态，其他任务不直接修改；这有助于集中序列化写入和取消策略。不过如果写任务自己仍被随意取消，或队列没有关闭/排空设计，问题并没有消失。它是把职责显式化，不是一个自动保证可靠性的魔法工具。

不要同时引入数据库、JWT、Redis、消息队列和微服务。每次只解决一个实际问题，并写出“为什么现在的方案不够、换完以后应该保持什么行为”。如果你能清楚解释这一点，工程能力已经比堆很多技术名词更扎实。

每天的小复盘

记录三件事：今天新增了哪一个不变量；哪个测试证明它成立；还有哪个失败时序没有覆盖。比如“只有成功替换文件后才更新内存”是一个不变量，“取消文件任务时的磁盘状态”仍是未覆盖边界。把这两者分清，比把所有测试都叫‘稳定可靠’更有价值。

19 · 自测、术语表和下一轮阅读

1. async 函数调用后，函数体一定马上执行吗？

不是。调用普通 async fn 先产生 Future；由 await、spawn 或其他执行器路径推动它。参数表达式仍按普通 Rust 规则求值，不要把“函数体惰性执行”误解为整个调用表达式都没有动作。

2. 一个 handler 里的 .await 会让整台服务器暂停吗？

正确实现的异步等待通常只让当前任务等待，运行时可推进别的任务。但同步阻塞、长 CPU 计算或过长的共享锁持有时间，会通过不同机制影响其他请求。

3. 为什么使用 Arc 后仍然需要锁？

Arc 负责共享所有权。是否能并发读写里面的值，仍由类型规则和锁等机制决定。Arc::clone 不复制文章，Vec<Post>::clone 通常会复制文章数据。

4. 写锁跨 await 是不是一定写错？

不一定。异步锁可以跨 await，本项目用它把整个保存过程串行化。代价是等待同一锁的请求延迟增加；若要缩短范围，必须同时解决丢更新、提交顺序和取消安全。

5. TCP 保证可靠，为什么我还要给消息加长度？

可靠和有序描述字节传输，不定义你的消息边界。长度前缀属于应用协议，帮助从任意 read 切片重建完整消息。

6. 服务端发回 201，但客户端超时了，重试一定安全吗？

不一定。客户端可能没收到已成功提交的响应；当前创建接口不具备幂等键，重试可能新增第二条记录。

7. timeout 能撤销已经发生的文件写入吗？

不能承诺。它结束本地等待，不自动回滚外部副作用。底层阻塞操作可能仍继续；需要设计事务、提交工作单元或补偿流程。

8. RwLock 能保护两个 Linux 进程共享 JSON 吗？

不能。这是进程内同步原语。多实例共享数据必须依靠跨进程协调或数据库等有明确并发协议的存储。

术语 一句话
Future 可被轮询推进、最终产生输出的计算状态
Task 被运行时调度的异步执行单元
Executor / runtime 负责推进任务，并提供相关 I/O、定时器等支撑
Waker 通知任务可能可以继续执行的句柄
Guard 代表已经取得的锁许可，离开作用域时释放
Backpressure / 背压 把有限处理能力传回工作来源，限制积压
Framing / 分帧 从连续字节中识别完整应用消息
Cancellation safety 取消与重建操作时是否保留所需进度/不变量
Idempotency / 幂等 同一个逻辑操作重复请求不产生额外效果
Graceful shutdown 停止接新工作，并按策略处理已有工作后退出
